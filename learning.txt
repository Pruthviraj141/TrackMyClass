Part 1 — Concepts, explained simply

What a CNN is and why it's used for images (vs a regular neural net):
A Convolutional Neural Network (CNN) is a type of AI designed specifically to look at pictures. Imagine trying to find a face in a photo by looking at a long list of pixel colors—it would be nearly impossible. Regular neural networks treat images as one long list. CNNs, on the other hand, look at small patches of the image (like a 3x3 square of pixels) and sweep across the whole picture. This allows them to recognize patterns like edges, shapes, and eventually complex features like eyes or noses, regardless of where they are in the picture.

What MTCNN does and how it differs from older methods like Haar cascades:
MTCNN stands for Multi-task Cascaded Convolutional Networks. It's essentially a three-stage filter designed to find faces and facial landmarks (like eyes, nose, mouth corners) in an image. Older methods, like Haar cascades, used hardcoded rules (e.g., "the eye region is usually darker than the cheek region") which often failed if lighting was bad or the face was tilted. MTCNN uses deep learning to learn what a face looks like from thousands of examples, making it much more robust to different angles, lighting, and occlusions.

What FaceNet does, what an "embedding" is (the 512-d vector), and why turning a face into a vector is more useful than comparing raw pixels:
FaceNet takes a cropped face image and runs it through a very deep CNN (InceptionResnetV1) to produce a list of 512 numbers. This list is called an "embedding". If you take two pictures of the same person, their 512 numbers will be very similar. If you take pictures of two different people, the numbers will be very different. Comparing raw pixels is terrible because if a person smiles or moves a bit to the left, almost every pixel changes. But their FaceNet embedding stays roughly the same, because it represents the underlying identity, not just the raw picture.

What triplet loss is and why FaceNet is trained that way:
When FaceNet was being trained, it used a technique called "triplet loss". Imagine three pictures: an "anchor" (a picture of Person A), a "positive" (another picture of Person A), and a "negative" (a picture of Person B). The AI is penalized if the anchor and positive are far apart, or if the anchor and negative are too close together. By repeatedly adjusting its internal weights to pull pictures of the same person closer and push pictures of different people apart, FaceNet learns how to generate those highly accurate 512-number embeddings.

What cosine similarity measures and why it's used instead of e.g. Euclidean distance here:
Cosine similarity measures the angle between two vectors (lists of numbers). If two vectors point in the exact same direction, their cosine similarity is 1.0 (a perfect match). If they are perpendicular, it's 0. We use cosine similarity instead of Euclidean distance (measuring straight-line distance) because embeddings are often normalized to have the same length. Cosine similarity focuses entirely on the "direction" of the vector, making it a very reliable way to see if two face embeddings are pointing to the same identity, regardless of slight magnitude variations caused by lighting.

Why the embeddings are cached in memory instead of recomputed/re-queried every frame:
In our system, we pull all the 512-number vectors of registered students from the database into RAM when a session starts. This is because video has 30 frames every second. If we queried the database for every single frame to do the math, the database would crash and the video would lag terribly. By keeping them in memory as a Numpy matrix, we can do the cosine similarity math for a newly detected face against all students in a tiny fraction of a millisecond. (As you'll see in our benchmark numbers, checking hundreds of students takes almost no time in RAM!)

What temporal tracking does and the false-positive problem it solves:
AI models can sometimes hallucinate. For one split-second frame, the model might think a random shadow looks like a face, or it might incorrectly match a student due to a weird angle. Temporal tracking is a buffer system. It says, "I won't mark attendance unless I see the same person consistently over the last 4 frames." This virtually eliminates false positives because while an AI might make a random mistake on one frame, it almost never makes the exact same mistake on 4 consecutive frames.

What a singleton pattern is and why it matters for the ML models specifically:
A singleton is a programming pattern that ensures a class or object is created only once. Deep learning models like MTCNN and FaceNet are huge. Loading them into memory can take several seconds and gigabytes of RAM. If we loaded them every time someone called an API endpoint, our server would freeze. By using a singleton, we load them exactly once when the server starts, and every subsequent request just reuses that already-loaded model instantly.

Part 2 — This project's actual numbers

When our system starts up, it takes about 24.2 seconds to load the deep learning models (MTCNN and FaceNet) into memory. But because we use a Singleton pattern, this only happens once.
For each frame of video:
- Detecting a face and cropping it (MTCNN) takes about 140 ms.
- Converting that face into a 512-dimensional vector (FaceNet) takes about 47 ms.
- Comparing that vector to hundreds of cached vectors in RAM takes practically 0 ms (under 2 ms even for 5000 students).
End-to-end, a single frame takes around 187 ms to process on a modern CPU, meaning the system can comfortably handle about 5.3 frames per second. The entire system uses about 550 MB of RAM while running.

Part 3 — Likely interview questions and how to answer them

"Walk me through how this works end to end"
Answer: Sure! When a class session starts, all student embeddings are loaded from the database into a fast in-memory cache. Then, the webcam starts streaming frames. For each frame, we first use MTCNN to detect and crop any faces. Then, we pass those cropped faces through our FaceNet model to generate a 512-dimensional embedding vector. Finally, we use Numpy to calculate the cosine similarity between this new vector and all the vectors in our cache. If we find a high-confidence match, and the temporal tracker confirms we've seen this person consistently for the last few frames, we log their attendance in the database.

"Why FaceNet instead of just training your own CNN?"
Answer: Training a CNN from scratch to recognize faces requires millions of images of thousands of different people, plus huge GPU clusters and weeks of training time. It's reinventing the wheel. FaceNet (specifically the InceptionResnetV1 architecture trained on the VGGFace2 dataset) has already learned the generic features of human faces. By using it, we don't need to retrain the model when a new student joins; we just generate their embedding and store it. It's a standard industry practice called transfer learning / feature extraction.

"What happens if someone holds up a photo instead of their real face?"
Answer: Honestly, right now, it would probably mark them present. That's a known vulnerability called a "presentation attack" or spoofing. Currently, MTCNN and FaceNet only check if a face exists and who it belongs to, not whether it's a 3D living person. In the next phase of this project, I plan to add liveness detection—either by requiring the user to blink/smile, or by integrating a separate lightweight model that detects screen glare or paper textures. But for this baseline phase, it's purely recognition.

"How would this scale to 10,000 users?"
Answer: The face detection and embedding generation steps take the exact same amount of time regardless of how many users there are, because they only process the incoming frame. The bottleneck would be the matching step. However, because we use vectorized Numpy matrix multiplication for cosine similarity in RAM, comparing one face against 10,000 cached embeddings takes less than a millisecond on a modern CPU. So for 10,000 users, the current architecture scales beautifully. Beyond that, say 1 million users, we'd need to swap the Numpy cache for a dedicated Vector Database like Qdrant or Milvus.

"Why cache embeddings in memory instead of querying the DB each time?"
Answer: Speed. We're processing video, potentially at 10 to 30 frames per second. If we did a network call to Firebase or even a disk read to SQLite for every face in every frame, the latency would be unacceptable and the DB costs would skyrocket. RAM is incredibly fast. By loading the embeddings once at the start of a session, the matching step becomes a pure CPU math operation, which is virtually instantaneous.

"What's the biggest weakness of this system right now?"
Answer: Besides the lack of liveness detection, the biggest weakness is that it's currently running on CPU (since I'm targeting accessible deployments). While Numpy makes the matching fast, the deep learning inference (MTCNN and FaceNet) is heavy. Processing a single frame takes around 187 ms, which limits our maximum FPS to about 5.3. If there are 20 faces in a single frame, FaceNet has to run 20 times sequentially. If I had more time, I'd implement batching for the FaceNet step, or deploy it on an edge device with a dedicated NPU or GPU to handle dense crowds in real-time.
