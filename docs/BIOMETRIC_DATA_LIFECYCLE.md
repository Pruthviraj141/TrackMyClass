# Biometric Data Lifecycle

## 1. Scope of Biometric Information
To execute Face Recognition properly, the system processes two discrete components of Biometric data:
1. **Raw Frames (Image Tensors):** The base64-encoded JPEGs sent via the client.
2. **Face Embeddings:** The 512-dimensional vector floats generated by Google FaceNet acting as a numerical summary.

## 2. Retention Policy
* **Raw Frames:** Never persisted directly to the backend database nor logged. They hit PyTorch via standard memory and get immediately garbage-collected globally upon response.
* **Embeddings:** Saved permanently into the local SQLite file directly keyed against standard user information as `/api/v1/registration/register` invokes profiling. 

## 3. Embedding Exposure
Student Embeddings are strictly restricted endpoints.
Even Admin/Teacher roles fetching the Student databases (`GET /api/v1/registration/students`) possess their payload forcefully scrubbed of `embedding` arrays (`[]`) ensuring network intercepts or compromised teacher accounts cannot reverse-engineer student FaceNet representations. Only the PyTorch `RecognitionEngine` explicitly possesses permission to retrieve arrays internally.

## 4. Environment Risks
If a malicious party gains host access and dumps `trackmyclass.db`, embeddings are visible plainly. While AES-256 block-level encryption of the `embedding` column might mitigate this heavily, executing block-ciphers on SQLite directly bottlenecks the Phase 1 goal structure. Hence, this platform assumes standard OS/App-level security over the Database.
